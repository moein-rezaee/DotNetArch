# Acceptance criteria

Verification: per-layer tests under `tests/` (D-17) plus `scripts/smoke.sh`, which generates into a temp dir, then builds and tests the output.
Nothing is claimed verified unless the script ran; when the SDK is unavailable the item stays unticked in the roadmap.

- AC-1 (R-A1..A8) Generated v2 solution builds; project references match the dependency rule in `architecture.md`; Application has no reference to Infrastructure or Kit Core/Providers; each layer csproj lists only its needed packages.
- AC-2 (R-A4) `new crud Product` creates `Features/Products/{Commands,Queries,Actions?,Dtos}/<Name>/...`; `new action` adds under `Actions/<Name>/` of the same entity folder.
- AC-3 (R-A9,A10) Setting a secret only in env and a non-sensitive value only in appsettings both appear in `IConfiguration`; examples contain every key used by options; validate script passes.
- AC-4 (R-A11,A12) `docker compose build` works for the Api; git repo initialised with initial commit unless `--no-git`.
- AC-5 (R-A13) Generated `<App>.Mcp` lists one tool per controller action, calls MediatR, and a unit test proves tool == controller result.
- AC-6 (R-A14) Each layer has a test project; `dotnet test` passes on a freshly generated solution. The tool repo has tests only for layers that need them (D-17).
- AC-7 (R-A15) For remotes github.com / gitlab.* / azure / bitbucket the matching CI file is produced; unknown host stores a choice; `--docker-registry` and `--nuget-source` appear in NuGet.config, CI and compose without credentials.
- AC-8 (R-B1,B2) `new service` internal mode output unchanged from v1.2.0; external mode produces a kit, not a service.
- AC-9 (R-B3..B8) `new kit --area Cache --providers Redis,InMemory` produces `kits/Cache/{Abstractions,Core,Providers.Redis,Providers.InMemory}`, builds standalone, packs with distinct versions, and `add kit Cache` wires Abstractions into Application and Core+Providers into the composition root only.
- AC-10 (R-C1) An MCP client can list tools from `dotnet-arch mcp serve` and create a solution and an entity; results list file paths.
- AC-11 (R-D1..D5) Tool repo, generated project and generated kit each contain AGENTS.md, specs, README pair; the bilingual-pair check script passes.
- AC-12 (D-10) Generated code contains none of the listed sample defects (grep-based check in smoke script: no `GetAwaiter().GetResult()`, no `IQueryable` in `IRepository`, no `AllowAnyOrigin` default, no stack traces via Console).
- AC-13 (D-11) Generated output restores from public NuGet only.
- AC-14 (R-F1..F3) `dotnet-arch doctor` on a freshly generated v2 solution reports no errors; on a repo with an upward project reference, a secret in appsettings or a kit Core/Provider package in Application it reports DA-S03 / DA-C05 / DA-K06 as errors and exits `3`; `--json` and the MCP tool `doctor` return the same findings; profile rules come only from `profile.yml`.
- AC-15 (R-G1,G2) `adopt` without `--apply` writes nothing; with `--apply` it writes only inside `.net-arch/`, every source file keeps its hash, a second run plans 0 changes, and deleting `.net-arch/` leaves the doctor findings unchanged.
- AC-16 (R-G3) `fix` creates only missing hygiene files / ignore lines, never edits code, and plans 0 changes on the second run.
- AC-17 (R-G4,G5) Every registry operation is an MCP tool with the same name and description, mutating tools declare `apply`, and rules.yml severity/exceptions change the doctor result (accepted exceptions are listed, not hidden).
- AC-18 (R-G3) The structural `fix` rules are opt-in: without `--rules` they are only listed as manual; DA-B03 keeps every resolved package version, DA-S04 creates a Domain test project without inline versions when central packages are used, and DA-S06 moves projects to `src/` and tests to `tests/`, rewrites every path that points at them, leaves history documents untouched and plans 0 changes on the second run.
- AC-19 (R-H1) `fix --rules=DA-A01` renames `tests/` to `test/`, rewrites solution, project references, Dockerfile/CI/compose paths and code path literals, leaves history documents untouched, keeps every test passing and plans 0 changes on the second run.
- AC-20 (R-H2) `fix --rules=DA-A02` creates a layer project only together with the files that move into it, keeps every moved file byte-identical, wires references, packages, `InternalsVisibleTo` and Dockerfile restore lines, registers the projects in the solution, creates no empty layer (unless `--empty`), keeps all controllers back when one cannot move, and plans 0 changes on the second run. A real service (Catalog) builds and passes its tests unchanged after the move.
- AC-21 (R-H3,H5) With `standards: [abp]`, `doctor` reports DA-A01..DA-A11 with locations and fix hints; without it none of them appears; an exception in `rules.yml` moves a finding to the accepted list.
- AC-22 (R-H4) A solution generated with `--layout=v3` builds, its tests pass and `doctor` with `standards: [abp]` has no DA-A error.
- AC-23 (R-H6) `fix --rules=DA-A08` generates an interface and a class per controller with the route, verb, route/query/body parameters and response type of every expressible action, lists the others as manual with a reason, references only Application.Contracts, compiles, and plans 0 changes on the second run. On Catalog it covers all 45 pinned routes.
- AC-24 (R-H7) `fix --rules=DA-A09` moves a root Compose file to `etc/docker/`, re-bases build context, env files and bind mounts so `docker compose -f etc/docker/<file> config` resolves the same files, leaves history documents alone and plans 0 changes on the second run.
- AC-25 (R-H8) `doctor` DA-A10 flags a loose project-root file and a folder with more than twelve files; `fix --rules=DA-A10` moves them into kind/feature folders inside the project with namespaces unchanged, keeps `AssemblyMarker.cs`-style composition files, and plans 0 changes on the second run.
- AC-26 (R-H9) `doctor` DA-A11 reports a missing reference, a forbidden unused reference, a project outside the solution and a missing Dockerfile restore line; `fix --rules=DA-A11` repairs them.
- AC-27 (R-I1) The registry lists every documented command; each is reachable from the CLI by its words and is an MCP tool with the same name and description; no tool is marked destructive; mutating tools declare `apply`.
- AC-28 (R-I1) `new solution` without apply writes nothing and lists the files; with apply it creates them. `new crud` without apply leaves the solution unchanged.
- AC-29 (R-I3,I4) A solution generated with layout v3 plus `new crud`, `new action` and `new event` builds with 0 warnings, passes its tests, has the ABP layer projects and a typed client, and `doctor` reports no DA-A finding.
- AC-30 (R-I2) `add_layer` creates a layer only when something moves into it and `add_tests` adds a registered test project; the MCP schema of `add_layer` has no `empty`.
- AC-31 (R-I5) After `new crud` then `new action` in a v3 solution the client has the new action, the client test project passes (including route parity) and a second `fix --rules=DA-A08` plans 0 changes.
- AC-32 (R-I6) With `folder_moves: [{from: ocelot, to: etc/gateway}]`, DA-A12 moves the folder and rewrites `COPY --from=build /src/<repo>/ocelot/`, `Include="..\\..\\ocelot\\*.json"` and `ocelot/*.json` in docs, while `/app/ocelot`, `Link="ocelot\\..."` and `ocelot/config-paths/*` stay; the second run plans 0 changes.
- AC-33 (R-J1) `new solution --in-place` into a folder that already holds `AGENTS.md` creates the solution in that folder, creates no folder named after the solution and leaves `AGENTS.md` unchanged.
- AC-34 (R-J2) `new action --input="Code:string,DeviceName:string?" --output="Token:string"` writes the request, the result, a stub handler, the validator, the controller action and (with MCP/CLI hosts) the tool and the command; `--output=none` returns 204; `--anonymous` adds `[AllowAnonymous]`; an unsupported type or a duplicate property is rejected before anything is written; a solution with such a use case builds with 0 warnings and its tests pass.
- AC-35 (R-J3) `add_cli` adds the host, its tests and a command per entity, action and use case; a solution with API, MCP and CLI hosts builds with 0 warnings, its tests pass and the parity test shows the same names on both sides; `doctor` has no error.
- AC-36 (R-J4) With a profile that lists kits, `new solution --profile` adds each package once to `Directory.Packages.props` and only to the listed projects, puts the lines of each host at its markers in the right order (bootstrap before the builder is created, builder lines after the configuration load, app lines after the host is built), writes the settings, secret keys and test values, removes the replaced Swagger and exception-handler code, and a second run changes nothing; an unknown host or replaced part is rejected. A solution generated with the Corevia profile (config loader, config center, secret store, logging, Swagger, error handling, JWT, service discovery) plus entities and a typed use case builds with 0 warnings and its tests pass.
- AC-37 (R-J5) `new entity` writes the entity (constants, private setters, `Create` with required parameters first), the EF mapping with lengths, enum-as-string and indexes, the DTO and mapping, a domain test and a persistence test, no CRUD files; an unknown enum, an unsupported type, a length on a non-string or a base-class property is rejected before anything is written; a solution with such an entity builds with 0 warnings and its tests pass.
- AC-38 (R-J6) `new feature` writes the controller and MCP tools skeleton; `new action --entity=<Feature>` without an explicit output is rejected; with one it writes the use case, the typed client follows and the build has 0 warnings.
- AC-39 (R-J8) A string input with `(n)` is validated against `n` and the plain one against 512; `(0)` is rejected; a feature whose controller already sits in the HttpApi project gets no second controller in the Api project.
- AC-40 (R-J9) A blueprint plan writes nothing; applying it creates its enums, entities, features, use cases (with the DTO of another entity resolved) and services; applying it again changes nothing; a nameless entity is refused before any file is written; the typed string lengths are recorded in `dotnet-arch.yml`.
- AC-41 (R-J10) The generated `IRepository` has `newestFirst` and `CountAsync`; the EF adapter orders descending when asked.
- AC-42 (R-J11) A blueprint without `schema` or a semver `version` is refused; a lower version and a changed file under the same version are refused; the lock records the applied version; the doctor reports DA-BP01..05 and `fix --rules=DA-BP03,DA-BP05` applies the blueprint until the doctor is clean.
- AC-43 (R-J12) A GET with a `[FromQuery]` record gets a typed client method; an ignored `.env` is not DA-C04; `fix --rules=DA-M09` adds the snapshot test and `UPDATE_OPENAPI_SNAPSHOT=1 dotnet test` writes `docs/api/openapi.json`; applying a blueprint restores the recorded lengths.
- AC-44 (R-J13) Deleting the blueprint of a generated service and running `fix --rules=DA-BP01 --apply` brings back an equivalent blueprint and leaves no DA-BP finding.
- AC-45 (R-J14) `fix --rules=DA-D03 --apply` puts `USER $APP_UID` before the ENTRYPOINT of a `dotnet/aspnet` final stage and the finding is gone; a Dockerfile on another base image is listed as manual and not changed.
- AC-46 (R-J15) `fix --rules=DA-G01 --apply` writes `dotnet-arch.yml` for an adopted service and the finding is gone; a hand-written MCP host is not recorded; writing a file with the same bytes is not a change in a plan.
- AC-47 (R-J16) `add_persistence --apply` creates the skeleton, wires `Program.cs`, raises older pins, never overwrites a file, changes nothing when repeated, and refuses a service with an EF context.
- AC-48 (R-J17) `add_tenancy --apply` wires the kit, scopes every entity, filters and stamps in the context and changes nothing when repeated; a context it cannot patch is listed as manual; a profile without the Tenancy kit is refused; DA-TN01 names the unscoped entities and `fix` clears it.
- AC-49 (R-J18) `fix --rules=DA-K04` lists the configured origins; `fix --rules=DA-M09` writes a snapshot test over the controllers when the tests have no application host.
- AC-50 (R-J19) A generated service has no DA-M10 or DA-B10 finding; `fix --rules=DA-M10,DA-B10 --apply` links the two documents of a pair and adds `<Version>` to the Api project of a service that lacks them.
- AC-51 (R-J20) `scaffold_kit` writes the packages, tests, docs and the package-list entry and refuses an existing area or a name that is not PascalCase; `scaffold_provider` adds the provider to the package list, the tests and the docs lists and refuses an unknown area or an existing provider; a plan writes nothing. A controller with `IgnoreApi = true` gets no typed client.
- AC-52 (R-J21) `add_tenancy --wire_only` wires the kit, adds no `ITenantOwned`, patches no entity or context, and changes nothing when repeated.
- AC-53 (R-J22) After `migrations add`, the migration files have no byte order mark when the editorconfig says `charset = utf-8`, keep it for `utf-8-bom`, and a missing folder or editorconfig is not an error (3 tests in `MigrationFilesTests`).
