# DotNetArch - Requirements (source of truth)

Every statement the owner gave is recorded here with a stable ID. Nothing may be dropped or
weakened without an entry in `docs/decisions/decisions.md`. Persian mirror: `requirements.fa.md`.

Status legend: `[ ]` not started, `[~]` in progress, `[x]` done and verified. Status is tracked in
`docs/ROADMAP.md`, not here.

## A. Generated microservice (target architecture)

- R-A1. Clean Architecture; layers are separate projects.
- R-A2. Ports and Adapters: Application/Domain own the ports (interfaces); Infrastructure/Api own adapters.
- R-A3. Vertical Slice + CQRS + Unit of Work + Repository pattern combined.
- R-A4. Queries, Commands and Actions are nested folders inside their own entity folder (one entity = one feature folder).
- R-A5. CQRS dispatching uses MediatR, as in the reference sample (see D-04).
- R-A6. Follow Clean Architecture, Clean Code and SOLID.
- R-A7. Correct wiring: each layer registers its own dependencies through its own DI extension (`AddXxxDomain/Application/Infrastructure/...`); the composition root only calls them.
- R-A8. Package (NuGet) references follow the same rule: each layer references only the packages it needs; no package leaks to a layer that does not use it.
- R-A9. Configuration: environment variables hold secrets and run-time values; `appsettings.json` holds non-sensitive settings. Both are loaded into `IConfiguration` when the project loads (single configuration-load step).
- R-A10. `.env.example` and `appsettings.example.json` are generated and kept in sync with the code.
- R-A11. Docker support (Dockerfile, compose, .dockerignore).
- R-A12. Git support (init, .gitignore, initial commit, remote/host configuration).
- R-A13. MCP support in the generated project: an MCP host whose tools mirror the project's controllers/services (same Application commands/queries, no duplicated logic).
- R-A14. Test support: a test project per layer, generated ONLY for generated projects (not for the DotNetArch tool itself, see D-02).
- R-A15. CI support: the tool picks the matching CI option itself (see D-06); supports personal/self-hosted git hosts; supports a personal Docker registry and a personal NuGet feed.

## B. `new service` (external services become Kits)

- R-B1. Two modes exist. Internal service (has business logic): keep current behaviour (correct as is).
- R-B2. External service (no business logic): the current behaviour is WRONG and is replaced by Kit generation.
- R-B3. A Kit has: an Abstractions package (clean-code/clean-architecture contracts), a Core package (options binding, provider selection, shared implementation, single `AddXxx(configuration)` entry point) and N Provider packages (can grow or shrink).
- R-B4. Kits are named after the capability, never after the product: `Cache` (providers: Redis, InMemory...), `MessageBroker` (provider: RabbitMq...), `MediaStorage` (providers: Minio, RustFs). No "Redis kit" or "RabbitMQ kit".
- R-B5. The reference kit is `samples/MediaStorage`; its structure, docs and rules are the template.
- R-B6. Kits are completely independent: their own versioning, buildable in CI, pushable to a personal NuGet registry, consumable by any service.
- R-B7. Kits live in one folder (`kits/`), grouped by business area: `kits/MediaStorage`, `kits/Cache`, `kits/MessageBroker`.
- R-B8. A kit is added to a service through its Abstractions in Application, its Core + Providers in the composition root only.

## C. DotNetArch tool as an MCP server

- R-C1. A separate MCP mode for using the library/tool itself: an agent can create solutions, entities, CRUD, actions, events, enums, constants, services/kits through MCP tools. (Distinct from R-A13.)

## D. Documentation, specs, rules

- R-D1. Complete documentation for the tool, the generated project and the kits.
- R-D2. Spec-driven development: specs (`openspec.yaml`, `testspec.yaml`, overview/contracts/acceptance/changelog) exist in the tool repo, generated projects and kits; behaviour changes update specs in the same change.
- R-D3. Agent-driven development: `AGENTS.md` with rules and best practices in the tool repo, generated projects and kits.
- R-D4. Bilingual pairs (`.md` + `.fa.md`) kept in sync, like the sample.
- R-D5. Best-practice rules follow the owner's description, NOT the reference sample blindly (see D-10).

## E. Process

- R-E1. Documentation, specs, rules and roadmap come FIRST; no decision and no point may be lost.
- R-E2. Roadmap lives in the project, phased; every executed item is ticked; if credit runs out, the roadmap shows the exact resume point.
- R-E3. Work proceeds phase by phase; each phase is committed and pushed to `claude/exciting-fermi-b41fue`.
- R-E4. Fix the sample's defects found during review instead of copying them (see D-10).
- R-E5. Show the final tree to the owner (`docs/specs/architecture.md`).

## F. Doctor (existing repositories)

- R-F1. `dotnet-arch doctor [path]` diagnoses an existing repository against the standard without changing it: layers and dependency direction, test projects, build hygiene, configuration and secrets, Docker/CI, bilingual docs, code rules and kit boundaries.
- R-F2. Organisation rules come from a declarative profile (`.net-arch/profile.yml` or a shared file it references); the tool contains no organisation-specific check. A profile may accept other layouts than v2.
- R-F3. Output for humans (text) and agents (`--json`, MCP tool `doctor`); findings carry id, severity, locations and a fix hint. Exit code `3` when blocking (errors, or warnings with `--strict`).

## G. Adoption and independence

- R-G1. `adopt` brings an existing project under tool control by writing only `.net-arch/` (state derived from the source, rules, profile reference, generated.lock); it changes no source file and is repeatable.
- R-G2. The project never depends on the tool: deleting `.net-arch/` breaks neither build, tests, Docker, CI, documentation nor MCP.
- R-G3. `fix` restores the standard only where the change is mechanical and cannot alter behaviour (hygiene files, ignore lines); it plans first and writes only with `--apply`.
- R-G4. One operation registry defines every operation once; CLI and MCP derive from it. Mutating operations return a machine-readable plan.
- R-G5. Settings: tool defaults < global `~/.net-arch/` < project `.net-arch/`; rules.yml carries severity overrides, thresholds and exceptions with a mandatory reason.
- R-G6. `doctor` also validates documentation (index, specs, OpenAPI snapshot) and tests (tests present, coverage versus threshold).

### ABP alignment (R-H)
- R-H1. Layout v3 (`src/`, `test/`, `etc/`) is supported by `adopt`, `doctor` and `fix`; v2 stays valid; `fix --rules=DA-A01` moves v2 to v3 and rewrites every path that points at the moved folders.
- R-H2. The layer projects `Domain.Shared`, `Application.Contracts`, `HttpApi`, `HttpApi.Client` are optional and exist only where there is something for them; `fix --rules=DA-A02` creates a layer together with the files that move into it (namespaces and in-project paths unchanged, references, packages and Dockerfile restore lines wired), lists what cannot move with the blocking file, moves controllers together or not at all, and creates an empty layer only with `--empty`. `doctor` DA-A07 flags a layer project without sources.
- R-H3. `doctor` has a built-in opt-in rule set `abp` (`DA-A01..DA-A11`), enabled by `standards: [abp]`; a profile can require it and can list accepted exceptions with a reason.
- R-H4. `new solution --layout=v3` generates the ABP-shaped tree (optionally with the layer projects) and passes the `abp` rule set.
- R-H6. `fix --rules=DA-A08` generates the typed client project from the controllers (only contract types; unsupported actions listed as manual); `doctor` DA-A08 reports a service with controllers and no client.
- R-H8. `doctor` DA-A10 flags loose files at a project root and folders crowded with several features; `fix --rules=DA-A10` moves them into kind and feature folders inside the project (namespaces unchanged); the typed client is generated into the same tree.
- R-H9. `doctor` DA-A11 checks project references (reachable, direction-respecting, no unused forbidden reference), solution membership and Dockerfile restore lines; `fix --rules=DA-A11` repairs them and lists a used forbidden reference as manual.
- R-H7. `fix --rules=DA-A09` moves root Compose files to `etc/docker/`, re-bases their relative paths and updates mentions; `doctor` DA-A09 reports root Compose files.
- R-H5. The tool has no rule about `Guid` ids, application services or ABP runtime features.
- R-I1. All commands (generators, ops, inspection) are operations of one registry; the CLI (`new crud`) and MCP (`new_crud`) surfaces are derived from it and list the same commands with the same values. A command that changes files returns a plan and writes only with apply.
- R-I2. `add_layer`, `add_tests`, `spec_list|add|check` and `graph` exist as registry operations; `add_layer` creates a layer only when files move into it, an empty layer is CLI-only (`--empty`).
- R-I3. `new solution` defaults to layout v3; in an ABP project every generator is followed by the ABP fixers and an `.net-arch/` refresh, and the generated solution builds without warnings, passes its tests and has no ABP finding.
- R-I4. The generated templates are fixer-friendly: DTOs are pure data, the entity mapping is a separate file, repository ports are async and return no `IQueryable`.
- R-I5. The typed client is generated with its tests (the verb and route of every action, and a parity test that every controller route has a client method) and follows the controller routes: an action added later, also in a partial controller file, reaches the client and its tests; `doctor` DA-A08 reports a client that is missing or out of date.
- R-I6. A profile can list root folders to move (`folder_moves`); `doctor` DA-A12 reports a pending move and `fix --rules=DA-A12` moves it and rewrites the paths that point at it without touching runtime paths, key paths, `Link` metadata, code or history documents.

### Corevia service enablement (R-J)
- R-J1. `new solution --in-place` creates the solution directly in the output folder (a repository folder that already exists, such as `corevia-<slug>`); existing files are never overwritten.
- R-J2. `new action` can generate a typed use case: `--input=Name:Type,...` and `--output=Name:Type,...|Type|none` give the request its own properties and result (scalars, arrays, lists, dictionaries, DTO names); the handler is a stub, the controller action, validator, MCP tool, CLI command and typed client follow, and the use case is recorded in `dotnet-arch.yml` so later hosts regenerate it. `--anonymous` marks a public endpoint.
- R-J3. `add_cli` (and `new solution --cli`) adds a CLI host `src/<App>.Cli`, a peer of the MCP host: both call the Application layer directly with the same MediatR requests as the API; every entity, action and typed use case gets a command; when both hosts exist a parity test keeps the MCP tool names and the CLI command names the same set.
- R-J4. A profile can list published kits (`external_kits`: packages with a central version and the projects that reference them, per host `usings` / `bootstrap` / `builder` / `app` lines, `settings`, `secrets`, `test_settings`, `replaces`); `new solution --profile=<file>` wires them into the Api, MCP and CLI hosts at the markers of their `Program.cs`, writes the settings, the `.env.example` keys, the configuration contract and the test-factory values, removes the generated parts a kit replaces (`swagger`, `exception-handler`) and references the profile in `.net-arch/profile.yml`. The tool names no kit; running the wiring twice changes nothing.
- R-J5. `new entity --entity= --properties=Name:Type[(max)][?][!|#],...` generates a domain entity with typed properties (string length, enum, optional, unique or plain index) and its persistence without CRUD use cases: the aggregate with a `Create` factory, the EF mapping, the DTO and its mapping, a domain test and a persistence test (round trip and unique indexes). `new enum --members=A,B` adds members after the generated `None = 0`. The repository port has `FirstOrDefaultAsync` and `ListAsync`.
- R-J6. `new feature --feature=Setting` generates a use-case group without an entity (controller and MCP tools skeleton); typed use cases attach to it with `new action --entity=<Feature> --input --output` (the output must be explicit).
- R-J7. `apply_profile --profile=<file>` wires (or upgrades) the `external_kits` of a shared profile in an existing solution with the same rules as `new solution --profile` (kit versions, host lines at the markers, settings, secret keys, test values); it is idempotent, plans first and writes only with apply. Sample values for string properties never exceed their declared length, so generated tests build entities with a `string(8)` property.
- R-J8. A typed input may set the length its string is validated against (`--input=Document:string(8000)`; the default is 512), recorded in `dotnet-arch.yml` like the rest of the use case. Once the controllers of a feature live in the HttpApi layer, `new entity`, `new feature` and `new action` never declare the partial controller again in the Api project (a second class on the same route).
- R-J9. `apply_blueprint --blueprint=<file>` generates what a blueprint (YAML) describes in one plan: `profiles` (as `apply_profile`), `enums`, `entities`, `features`, `use_cases` (entity, action, method, input, output, anonymous, description; the typed-use-case rules of R-J2 and R-J8), `services` (internal services) and `layers` (as `add_layer`), in that order, with the same generators as the single commands. What already exists (an enum, an entity, a feature, a recorded use case, a service file) is skipped, so a blueprint is applied again after it grows; a missing name is refused before anything is written. The blueprint is the spec of a service: it lives in the service repository (`docs/specs/blueprint.yaml`) and the CLI and the MCP tool come from the same registry entry. The length of a typed string input is recorded in `dotnet-arch.yml` (`Name:string(120)`), and a use case may return the DTO of another entity of the solution.
- R-J10. The generated repository port can page newest first (`GetPagedAsync(..., newestFirst: true)`) and count (`CountAsync(predicate)`), in the EF adapter and in every generated fake, so list and statistics use cases need no query of their own.
- R-J11. A blueprint is versioned. It carries `schema` (the format; the tool refuses a format newer than it reads) and `version` (semver, the version of the model). `apply_blueprint` records what it applied in `.net-arch/service-blueprint.lock` (file, schema, version, content hash), refuses a version lower than the applied one, and refuses a changed file under the same version, so every change of the model carries a new version. The doctor checks the blueprint without depending on any standards repository: DA-BP01 (no blueprint), DA-BP02 (it does not read, or lacks schema/version), DA-BP03 (described but not generated), DA-BP04 (generated entities or use cases the blueprint does not describe), DA-BP05 (not applied at its current version). `fix --rules=DA-BP03,DA-BP05` applies the blueprint with the same generators; it never edits the blueprint.
- R-J12. Doctor and fix: DA-A08 expresses a GET that binds a query record with `[FromQuery]` (one query-string value per property of the record, required ones first); DA-C04 is a finding only when a `.env` file is not covered by `.gitignore`; DA-M09 is fixed by a generated test (`OpenApiSnapshotTests`) that compares the running API's OpenAPI document with `docs/api/openapi.json` and writes it when `UPDATE_OPENAPI_SNAPSHOT=1`; applying a blueprint brings the string lengths recorded for existing use cases in `dotnet-arch.yml` in line with the blueprint.
- R-J13. `fix --rules=DA-BP01` writes the blueprint of a service that was generated before it had one: enums, entities (typed properties with lengths, nullability, unique and plain indexes and the properties left out of the DTO), features, use cases (as recorded in `dotnet-arch.yml`) and services are read back from the generated code and applied (the lock records version 1.0.0). It is a starting point to review; entities generated with `new crud` are not described by a blueprint.
- R-J14. `fix --rules=DA-D03` makes the final stage of a Dockerfile built on a .NET runtime image (`dotnet/aspnet`, `dotnet/runtime`) run as the image's non-root user: `USER $APP_UID` goes before the first ENTRYPOINT or CMD of the last stage. Any other base image stays a manual finding. The MCP tool `fix` and the CLI command are the same operation.
- R-J15. A service that was not generated by the tool (only adopted) is brought to the same footing mechanically. `dotnet-arch.yml` is read from the solution file, the Api project, the packages, the Dockerfile (`EXPOSE`), `NuGet.config` and `.net-arch/project.yml` (doctor DA-G01, `fix --rules=DA-G01`); every generator and `apply_blueprint` then run on it. An MCP host is recorded only when it is the tool's own (`Tools/ToolRunner.cs`): tools are never generated into a hand-written host. A plan compares files by content, so writing the same bytes again is not a change.
- R-J16. `add_persistence` gives a service with no EF context the standard persistence skeleton with the templates `new_solution` uses (domain base types, repository and unit-of-work ports, EF adapter, context, design-time factory, the MediatR pipeline, test support), merges the packages (raising, never lowering, an older central pin and an older `VersionOverride` of `Microsoft.Extensions.*`), writes the `Database` settings and wires `Program.cs`; existing files are never overwritten and a service that already has an EF context is refused.
- R-J17. `add_tenancy --profile=<profile with the Tenancy kit>` makes a service multi-tenant (tenant = Keycloak realm): the kit is wired (also into a `Program.cs` that has no markers), every entity the single EF context persists gets `ITenantOwned` and a `TenantId`, the context filters every query by the tenant of the caller (an operator, and a context with no caller, see every tenant), stamps the tenant on new rows and refuses a row with no tenant. The doctor rule DA-TN01 is opt-in (`adopt --standards=tenancy`) and `fix --rules=DA-TN01 --tenancy_profile=<profile>` runs the operation. What cannot be patched by text is listed as manual.
- R-J18. Three more mechanical fixes: DA-K04 (a host that allows any origin allows the origins of `Cors:AllowedOrigins`), DA-M09 for a service whose tests have no in-process host (a small host over its controllers makes the OpenAPI document), and the Dockerfile fix of R-J14.
- R-J19. Two more doctor rules with a fixer: DA-M10 (both documents of an English/Persian pair link each other near the top; `fix` adds the line) and DA-B10 (the Api project carries a `<Version>` that a release raises; `fix` adds `1.0.0`). The generated README and docs templates carry the language links, the standard README sections (Purpose, Scope, Prerequisites, Configuration, Run / Usage, Validation / Verification, Troubleshooting, Change Log, Ownership) and the version, so a generated service passes a documentation and version gate without hand work.
- R-J20. The tool creates the shared packages the services plug their ports into. `scaffold_kit` creates a Kit area in the Kit repository (Abstractions and Core packages, a test project, bilingual README, AGENTS and specs, and the entry in `Corevia.Kit.packages.proj`); `scaffold_provider` adds a provider package to an area (project, DI extension `AddCorevia<Kit><Provider>`, reference from the test project, package-list entry and the lists in the docs). Existing areas and providers are refused; names are PascalCase. Both are in the CLI and in MCP from the one registry. A controller marked `[ApiExplorerSettings(IgnoreApi = true)]` (a webhook for a platform) is not part of the typed client (DA-A08).
- R-J21. `add_tenancy --wire_only` only wires the tenancy kit (packages and host lines) for a service whose data lives in an external system of record (an accounting system): there is no tenant column to add, the tenant of the caller picks the connection instead.
- R-J22. A migration written by `dotnet ef migrations add` follows the solution's `.editorconfig`: EF writes UTF-8 with a byte order mark, so when the editorconfig asks for plain `charset = utf-8` the tool removes the mark from the migration files it just generated (and keeps it for `utf-8-bom`). A new service then passes `dotnet format whitespace --verify-no-changes` (the lint job) without a hand reformat.
- R-K1. A module becomes composable mechanically (Phase 15, D-40). `move_code` moves files between projects (or into a folder of one project) and rewrites the namespace, every `using`, qualified and partly qualified names, adds the project and package references the moved code needs (a namespace is matched against the assemblies of the restored package folder, not against a package id) and, with `--make_public`, declares moved types public. A using of a namespace that no longer exists is dropped; code that sat in the old namespace gets the using it now needs.
- R-K2. `add_composition --adapters=A,B` creates `<App>.Composition` with `Add<Module>Composition(configuration, registerBackgroundWorkers)`: it registers the module's Infrastructure and the adapter picked by a configuration key (default `ServiceProvider:DefaultProvider`; `--selector_env`, `--aliases` and `--regenerate` keep historical spellings), rewrites the call sites outside Infrastructure and adds the project references. The first adapter is the default.
- R-K3. `describe_module` writes `module.yaml` (ports, adapters with package, version, registration, the ports they implement and the configuration keys they read, layers, composition project, module version) and `describe_settings` writes `settings.schema.json` next to each project that declares options classes (JSON Schema 2020-12, closed, secrets `writeOnly`, nested classes inline). Both are derived: they change only when the code changes.
- R-K4. The adapters rule set (`standards: [adapters]`, DA-AD01..DA-AD06): an adapter (`<App>.Infrastructure.<System>`) depends on the module core only; the shared Infrastructure references no adapter; adapters do not reference each other; an adapter has a registration method; an adapter is a package whose id comes from the profile (`adapter_package`, no organisation in the tool) and whose version CI sets from the adapter's own tag through the property `AdapterVersion` (so the core packages it depends on keep the module version); the package carries its `settings.schema.json`. The profile key `non_adapters` names Infrastructure projects that are persistence. `fix` removes an unused reference, keeps as direct references the packages the removed project brought in, and writes PackageId and the schema item.
- R-K5. `scaffold_adapter` adds an adapter package to a Kit area (`Corevia.Kit.<Kit>.Adapters.<Adapter>`), the same as `scaffold_provider` with the vocabulary of the composition model (which stays for one release); and the adapters rule DA-AD07 reports a configuration key an adapter reads that its `settings.schema.json` does not define (a flat `KEY_LIKE_THIS` is never defined by a hierarchical schema: that is the debt TD-06 made visible).
- R-K6. DA-AD08: the module core projects an adapter depends on (Domain, Domain.Shared, Contracts, Application.Contracts, and what those reference) are packages at the module version (the `<Version>` of the Api project), with the id from the profile pattern `module_package` (tokens `{Module}`, `{Layer}`); otherwise an adapter package would depend on a package no feed has. `fix --rules=DA-AD08` writes PackageId, IsPackable and the version.
